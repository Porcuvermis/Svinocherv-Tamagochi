# Архитектура

## 0. Главное изменение по сравнению с текущим состоянием

Игра — **Telegram Web App с серверной частью**. Это не «сайт с localStorage»,
и проектировать её так нельзя.

Два следствия, определяющие всю архитектуру:

1. **Всё, что завязано на время, идёт от реального времени и работает при
   закрытой игре.** Потребности червя падают, пока приложение не запущено.
   Оффлайн-доход капает. Суточные лимиты и стрики считаются по календарю, а
   не по сессиям.
2. **Источник правды — сервер и его база.** Клиент — только отображение и
   ввод. localStorage перестаёт быть хранилищем состояния и становится кэшем
   для мгновенной отрисовки до прихода ответа сервера.

Заложить надо сейчас: позже перевод на серверную модель означает
переписывание каждого модуля.

## 1. Что не так с текущей структурой

```js
// main.js — так больше нельзя
setInterval(() => this.decaySins(), 500);

decaySins() {
    this.sins[key].value -= this.sins[key].decay * 0.5;
}
```

* Шкала падает только пока открыто приложение. Закрыл — заморозил. Это
  противоречит самой идее тамагочи.
* Состояние живёт в оперативной памяти и умирает при закрытии.
* Мини-игры пишут в `GameManager.sins.*.value` напрямую — награды размазаны
  по семи файлам.
* Нет валют, нет сохранения, нет причин зайти завтра.
* Сохраняется только модель персонажа (`worm-model.js` → localStorage).

## 2. Принцип «ленивого времени»

Ключевой приём. Состояние **не обновляется по таймеру**. Хранится последнее
известное значение и метка времени, актуальное значение вычисляется формулой
в момент обращения:

```
value_now = clamp(0, max, value_at - decay_rate * (now - updated_at))
```

Что даёт:

* шкалы падают одинаково, открыта игра или нет;
* никаких фоновых процессов, крутящих миллионы записей раз в секунду;
* один и тот же расчёт на клиенте (для плавной анимации) и на сервере (для
  правды).

Правила:

* `now` — **всегда серверное время**. Клиентские часы подделываются переводом
  системного времени. Клиент при старте получает от сервера timestamp и
  хранит поправку `serverOffset`, применяя её ко всем локальным расчётам.
* То же касается оффлайн-дохода, кулдаунов, стриков, суточных лимитов.
* Таймеры на клиенте остаются только для анимации: `requestAnimationFrame`
  плавно двигает полоску между значениями, но не является источником данных.

Оффлайн-доход и оффлайн-падение считаются при заходе, разово, за прошедший
интервал. У дохода есть потолок (~8 часов), у падения шкал потолка нет (но
есть пол в 0).

## 3. Клиент-серверная архитектура

### 3.1 Разделение

| Слой | Где | Ответственность |
|---|---|---|
| Клиент | GitHub Pages (статика) | рендер, ввод, анимация, локальный кэш, предсказание значений |
| API | отдельный хост | правда о состоянии, начисления, лимиты, валидация |
| БД | PostgreSQL | хранение |
| Бот | Telegram Bot API | вход в приложение, push-уведомления |

GitHub Pages не умеет бэкенд — API живёт на отдельном домене (Railway /
Fly.io / VPS / любой хостинг Node). Понадобится CORS.

### 3.2 Аутентификация

Telegram Web App передаёт `initData`. Сервер обязан проверять его подпись
HMAC-SHA256 на секрете бота, а не доверять переданному `user.id`. Без этой
проверки любой может выдать себя за любого игрока.

* Клиент отправляет `initData` один раз, получает сессионный токен (JWT,
  короткий TTL).
* Все дальнейшие запросы идут с токеном.
* `telegram_user_id` — первичный ключ игрока.

### 3.3 Модель доверия

Мини-игры считаются на клиенте, значит результат подделываем. На текущем
этапе это допустимо, но архитектура должна быть готова к ужесточению:

* Сервер никогда не принимает «начисли мне N золота». Клиент присылает
  результат (`sin`, `mode`, `outcome`, метаданные), сервер сам решает, что
  начислить, по своему конфигу наград.
* Все конфиги наград и цен живут на сервере. Клиент получает копию только
  для отображения.
* Каждый запрос на начисление несёт `client_request_id` (UUID). Повтор с тем
  же id не начисляет второй раз — защита от двойных тапов, потерянных
  ответов и ретраев.
* Rate limit по частоте: бой не может завершиться быстрее физического
  минимума.
* Все начисления пишутся в журнал транзакций (`ledger`). Без него невозможно
  ни разобрать баг, ни откатить накрутку.

### 3.4 Push-уведомления

Отдельное преимущество Telegram: бот может написать игроку. Главный
инструмент возврата.

* «Свиночервь голодает» при падении шкалы ниже порога.
* «Оффлайн-кошелёк заполнен».
* «Стрик сгорит через 3 часа».

Реализуется фоновой задачей: раз в N минут выбирает игроков, у кого
расчётное значение пересекло порог и кому ещё не отправлялось уведомление в
этом цикле. Обязательны настройка отключения и жёсткий лимит частоты, иначе
игрок заблокирует бота.

## 4. Схема базы данных (черновик)

Все временные поля — `timestamptz`, всё в UTC. Все денежные значения — целые
числа, никаких float.

```
players
  id                bigserial PK
  telegram_user_id  bigint UNIQUE NOT NULL
  username          text
  created_at        timestamptz
  last_seen_at      timestamptz     -- база для оффлайн-расчётов
  timezone_offset   int             -- для «суток» в стриках и ежедневках
  schema_version    int

currencies                          -- по строке на валюту, а не колонки
  player_id, currency, amount       -- 'gold','crystal','wrath_shard','wrath_token'
  PRIMARY KEY (player_id, currency)

sins
  player_id, sin
  value             numeric         -- значение НА МОМЕНТ updated_at
  max_value         numeric         -- растёт от мета-апгрейдов
  decay_rate        numeric         -- единиц в секунду
  updated_at        timestamptz     -- ключевое поле для ленивого расчёта
  PRIMARY KEY (player_id, sin)

sin_upgrades                        -- локальная прогрессия каждого греха
  player_id, sin, upgrade_key, level

worm
  player_id PK, model jsonb, stage int, cosmetics jsonb

scars                               -- шрамы гнева
  id, player_id
  zone              text            -- 'head' | 'body' | 'tail'
  t                 numeric         -- позиция вдоль скелета, 0..1
  seed              bigint          -- детерминированная генерация формы
  created_at

inventory        player_id, item_key, qty
unlocks          player_id, unlock_key, acquired_at

runs                                -- незавершённые забеги рогалика
  player_id, sin
  state             jsonb           -- карта, узел, HP, зубы, предметы, дебаффы
  difficulty, started_at, updated_at
  PRIMARY KEY (player_id, sin)

daily_counters   player_id, day_key, counter_key, value
pvp_snapshots    player_id PK, snapshot jsonb, updated_at

ledger                              -- журнал всех начислений и трат
  id, player_id, currency, delta, reason
  client_request_id UNIQUE, created_at
```

Замечания:

* `currencies` строками, а не колонками: добавление валюты нового греха не
  должно требовать миграции таблицы.
* `sins.updated_at` — сердце ленивого расчёта, обновляется при каждой записи.
* `daily_counters.day_key` вычисляется с учётом `timezone_offset`, иначе
  «сутки» будут неверными для половины мира.
* `ledger.client_request_id UNIQUE` — та самая идемпотентность.
* Обязательны миграции с номером версии. Схема будет меняться десятки раз.

## 5. API (черновик)

```
POST /auth/telegram   -> { token, serverTime, config }
GET  /state           -> полное состояние + serverTime
POST /minigame/result -> { sin, mode, outcome, meta, client_request_id }
POST /shop/purchase   -> { shop, item_key, client_request_id }
POST /run/start       -> { sin, difficulty, client_request_id }
POST /run/node        -> { node_id, choice, client_request_id }
POST /run/abandon
POST /scars/exchange  -> { count, client_request_id }
POST /daily/claim
```

* `/state` — единственный способ узнать правду. Клиент запрашивает при
  старте, при возврате из фона (`visibilitychange`) и после каждого
  начисления. Ответ всегда содержит `serverTime` — клиент пересчитывает
  `serverOffset`.
* Между запросами клиент предсказывает значения теми же формулами локально,
  чтобы полоски двигались плавно. При расхождении — плавно подтягивается к
  серверному значению, а не прыгает.

## 11. Модули клиента

```
src/core/
  net.js          — HTTP-слой, токен, ретраи, client_request_id
  time.js         — серверное время, serverOffset, все формулы времени
  state.js        — единый стор состояния, кэш в localStorage, синк с /state
  economy.js      — Economy.get/has, отображение валют (НЕ начисляет сам)
  events.js       — шина событий
  worm-model.js   — существующая модель (уезжает под state.js)
```

### Развязка мини-игр и экономики

Мини-игры не знают про экономику и про сервер. Они бросают событие:

```js
GameEvents.emit('minigame:result', {
    sin: 'wrath',
    mode: 'pve_duel',
    outcome: 'win' | 'lose' | 'draw',
    meta: { damageDealtPct, lastHitZone, turns }
});
```

Ядро ловит событие, отправляет на `/minigame/result`, получает от сервера
новое состояние и обновляет UI. Все правила начисления — на сервере, в одном
конфиге, а не разбросаны по семи модулям.

Заполнение шкал переезжает туда же: прямые записи вида
`GameManager.sins.wrath.value = 100` из `wrath.js` убираются полностью.
